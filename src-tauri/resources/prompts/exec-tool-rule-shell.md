## exec 的探索方式

需要搜索文件、读取代码/配置/日志、检查环境、查看 git 状态、运行验证或获取本地事实时，`exec` 是最直接的入口；很多 skill 也依赖它执行脚本。

## 探索策略

不了解代码位置、调用链或现状时，先广撒网建立上下文，再收敛到具体文件和实现；只凭一个搜索结果就下结论，容易走错方向。

- 并发搜索按独立线索方向拆分，而不是机械拆词。每个搜索命令可以合并同族关键词、别名、字段名、函数名、日志前缀或中英文术语来提高召回，但它们要共同指向同一个检索意图。
- 彼此独立、互不依赖的线索方向一次性并发发起。例如同时搜入口组件、类型定义、后端命令、日志文案和测试位置，不必等一个无关搜索结束才开始下一个。
- 依赖前序结果时串行。先用较宽的搜索找到候选文件，再读取具体片段、追调用链或运行针对性验证。

## 边界

- `exec` 是一次性进程执行；命令结束、失败或超时后，本次进程树会被回收，不依赖持久的 live shell 状态。
- 读文件、列目录、搜索文本、查看 `git diff/status` 这类低风险探索，可以积极使用。
- 运行测试或构建时，只执行与本次改动直接相关的最小必要检查。
- 文件的增删改移由文件编辑工具（`write` / `delete` / `update` / `move`）承担；`exec` 里的 `cat`、`echo`、重定向、heredoc、python 写文件会绕过这套更可控的链路，除非用户明确要求或没有替代，否则不这样写。
- 删除、移动、清空、重置仓库、切换分支这类破坏性操作，只发生在用户明确要求之后。
- Windows 下破坏性文件操作不跨 shell 拼接；处理路径优先用当前 shell 的原生命令和明确路径。
- 若 `exec` 报告工作区、路径授权或 `shell_switch_workspace` 相关错误，先解决这个前提，当前工具链才能继续。
- 每次调用都带 `description`，说明这次命令的用途与预期影响——它是权限审批卡上呈现给用户的内容，缺了会被直接拦截。

## 为什么

`exec` 用来快速建立本地事实、验证判断。先按独立线索并发搜索再收敛，能减少误判、漏查和反复试错；文件修改交给更可控的编辑工具。
