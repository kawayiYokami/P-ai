## 何时使用 plan
- 重构：大规模模块拆分、架构调整、技术栈迁移。
- 全新功能域设计：涉及多模块、跨前后端、接口协议或数据模型设计。
- 用户明确要求写计划。
- 常规功能迭代、简单 UI 改动、文档更新、小修小补等日常工作，直接实现。

## plan 和 todo
- 计划文档用于锁定需求、目标、边界、风险、统一口径、术语、应该有的测试和最终呈现。
- todo 用于承接计划确认后的 3~7 步当前执行。
- 最终形态只描述用户可感知结果、数据契约示例或验收样例。
- 实现开始后发现计划不准确，应优先修正计划或说明偏差。

## 计划文件
- 先把计划写成 Markdown 文件，再调用 plan。
- 优先写到：{preferred_plan_dir}
- 先按计划的主要业务产出选择一个领域目录，再写入 `.pai/plan/{domain}/`；可用领域包括 `chat`、`remote-im`、`runtime`、`tools`、`storage`、`memory`、`model`、`organization`、`ui`、`platform`、`release`。
- 文件命名使用 `.pai/plan/{domain}/YYYYMMDD_中文关键词.md`，日期统一使用 8 位数字。
- 不按 `active`、`archive` 或年月创建额外状态层级；计划完成后保留在原领域目录。
- 计划一旦提交，后续 `plan.present` 与 `plan.complete` 始终使用同一份物理路径，不要擅自移动已提交计划。
- 计划应包含：用户原始关键指令、目标、需求描述、风险、边界、统一口径、术语解释、应该有的测试；最终呈现结果和相关文件可按需补充。
- 用户原始关键指令只节选影响目标、边界、风险或验收的原文；用户口误后纠正时，采用纠正后的版本。
- `plan.present` 只提交 `path`。
- `plan.complete` 也只提交同一份 `path`。
- 局部修订计划时，优先补丁修改现有计划文件。

## 规划方式
- 写计划前先扫描核心上下文，确认用户目标、现状、风险和关键缺失项。
- 计划未定前，先做最小必要调查。
- 计划要约束需求边界，保持简洁。
- 遇到非显性分叉或明显成本差异，先和用户同步，再进入重度开发。
- 必须先得到用户明确确认后，才可进入实现阶段。
- 新信息进入后及时修正计划。
