# 远程联系人上下文管理说明

本文说明远程联系人体系中，不同角色、不同聊天类型和不同委托实际获得什么上下文。

私聊与群聊的状态流转，参见 [远程联系人状态机说明](remote_im_state_machine.md)。

重点区分：

- 私聊主助理上下文；
- 群聊秘书判断上下文；
- 群聊远程应答委托上下文；
- 群聊已有委托收到引导后的上下文；
- 群聊离场反思委托上下文；
- 群聊在场期间当前 block 的管理规则。

本文不把“秘书判断输入”和“助理正式上下文”混为一谈。

---

# 一、基础概念

## 1. 正式会话消息

远程联系人发送的文字、图片、音频和附件先写入绑定会话。

消息成功入库后才会触发后续调度。防抖、秘书和助理都不拥有消息，也不会把消息从会话中转移出去。

## 2. 当前 block

当前 block 是模型当前可以使用的连续会话上下文块。

群聊进入在场后，所有新消息持续追加到当前 block：

```text
当前摘要
→ 在场期间消息 1
→ 在场期间消息 2
→ ……
→ 指定结束锚点
```

必须满足：

- 消息按原始顺序连续排列；
- 不按群友过滤；
- 不跳过中间消息；
- 新消息不插入旧 block；
- 未完成防抖的锚点不能离开当前 block。

## 3. 结束锚点

结束锚点是某次调度允许使用的最后一条消息 ID。

锚点只限制上下文终点，不允许改变中间消息：

```text
合法：当前 block 起点 → 连续读取 → 锚点
非法：只挑选某个群友的消息 → 锚点
```

## 4. 秘书判断输入与助理正式上下文

两者用途不同：

```text
秘书判断输入
→ 用有限历史和本次新消息判断是否回答、由谁回答

助理正式上下文
→ 用当前完整连续上下文生成正式回复
```

秘书使用轻量范围，不代表正式助理只看到这段范围。

---

# 二、私聊上下文

## 1. 私聊没有秘书上下文

私聊完全禁用秘书，因此不存在：

- 秘书回复判断；
- 秘书防抖；
- 助理工作账本路由；
- `targetDelegateId` 选择；
- 群聊离场/在场上下文切换。

私聊消息天然就是用户直接交给当前助理的内容。

## 2. 私聊主助理空闲

绑定会话空闲时：

```text
私聊消息入库
→ 直接进入当前绑定会话
→ 主助理使用当前会话连续上下文
→ 启动新一轮回复
```

主助理获得的是绑定会话当前正式上下文，不经过秘书裁剪或判断。

## 3. 私聊主助理忙碌

绑定会话正在运行时，新私聊消息统一作为引导消息加入。

```text
当前主助理正在处理
→ 用户发送补充文字、图片或附件
→ 消息正常入库
→ 作为引导消息加入当前会话
→ 主助理在合法检查点继续处理
```

引导消息不会创建新的并发远程应答委托，也不经过秘书判断。

主助理后续读取的仍是当前绑定会话连续上下文，包括已经完成的工具过程和新加入的引导内容。

## 4. 私聊上下文总结

| 场景 | 执行者 | 获得的上下文 |
|---|---|---|
| 当前会话空闲 | 绑定会话主助理 | 当前会话连续正式上下文 |
| 当前会话忙碌 | 同一个主助理 | 原有上下文 + 新入库引导消息 |

私聊不存在独立秘书或独立远程应答委托上下文。

---

# 三、群聊在场上下文

## 1. 从离场进入在场

群聊离场期间，消息仍然入库，但助理不会因为普通群聊内容自动参与。

群友明确喊到助理后，助理防抖截止并准备首次应答。此时会完成离场到在场的上下文整理：

```text
旧历史
→ 整理为当前摘要
→ 保留触发消息及之后的当前 block
→ 启动远程应答委托
```

入场整理只负责收口离场历史。进入在场后，后续消息全部持续追加到同一个当前 block。

## 2. 在场期间

在场期间不得为每个防抖重复建立新的 block。

所有群友消息自然形成一条连续时间线：

```text
当前摘要
→ 张三消息
→ 李四消息
→ 张三图片
→ 王五消息
→ 张三结束锚点
```

即使某次助理防抖属于张三，正式上下文也必须包含锚点之前的李四和王五消息。

群友身份只决定哪个助理防抖更新，不决定正式上下文包含哪些消息。

## 3. 防抖期间

防抖只保存消息 ID和计时状态，不复制上下文：

- 助理防抖保存对应群友的起点和结束锚点；
- 秘书防抖保存会话级起点和结束锚点；
- 消息正文始终以当前 block 为真相源。

---

# 四、群聊秘书上下文

## 1. 秘书提示词的固定分层

所有秘书调用都必须严格拆成两层：

```text
系统提示词
→ 只放固定不变的角色、职责、规则和输出协议

第一个用户提示词
→ 放本次调用所有会变化的上下文数据
```

不得把动态联系人信息、历史消息或工作状态拼进系统提示词，也不得把秘书的固定职责和 JSON 协议重复塞进动态用户内容。

### 系统提示词必须包含

- 秘书的固定角色和职责；
- 秘书只做判断与路由，不代写正式回复；
- 普通审查允许不回答、新建或引导；
- 点名批次在已有委托时的忙碌路由必须回应，只能新建或引导；
- `targetDelegateId` 的固定使用规则；
- 无法确定时的固定判断倾向；
- JSON 字段、字段含义及禁止输出 Markdown 等固定协议。

系统提示词不得包含联系人、人格、历史消息、防抖消息、工作账本、活跃委托或其他本次调用才确定的数据。

### 第一个用户提示词必须包含

- 当前助理人格；
- 当前联系人名称、类型和必要标识；
- 联系人的“什么时候应该回答”配置；
- 最近有限条已处理历史；
- 本次防抖起点到结束锚点的连续新消息；
- 最新消息标识；
- 助理工作账本；
- 当前运行中的远程应答委托 ID；
- 本次是普通审查还是点名批次的忙碌路由。

动态数据集中放在第一个用户提示词，可以稳定复用系统规则，避免联系人上下文串线，并让快速请求记录完整展示本次秘书实际看到的数据。

### 消息结构示例

```text
system:
  你是远程群聊应答秘书……
  普通审查允许不回复……
  点名批次的忙碌路由只能新建或引导……
  只返回 { shouldReply, targetDelegateId, reason }

user（第一条）:
  当前助理：……
  当前联系人：……
  回答规则：……
  最近已处理历史：……
  本次连续新消息：……
  助理工作账本：……
  活跃委托 ID：……
  本次审查模式：普通 / 点名批次的忙碌路由
```

普通审查和忙碌路由必须复用同一分层，不得分别发明不同的提示词布局。

## 2. 已入场批次的普通 60 秒秘书审查

只有已经通过入场、且入场消息未点名的群聊批次才会创建秘书巡检。未通过入场的消息只入库，不会创建秘书审查；已入场批次的后续消息只追加，不会通过再次点名改写巡检等级。

防抖截止后，秘书获得：

```text
最近有限条已处理历史
+
防抖起点到结束锚点的连续新消息
+
助理工作账本
```

当前实现只读取：

- 起点之前的有限历史，用于提取最近 7 条有效秘书消息；
- 起点到终点的连续范围；
- 不整读整个当前 block。

秘书根据这些内容判断：

- 话题与助理无关：不回复；
- 应由新工作处理：创建新的应答委托；
- 应继续已有工作：返回 `targetDelegateId` 引导已有委托。

## 3. 巡检等待期间的后续消息

已有秘书巡检时，后续消息会追加到本批连续范围。

后续点名仍作为正式上下文的一部分，但不会升级为助理防抖、不会缩短 60 秒基础巡检，也不会强制秘书回复。

秘书到期后仍按普通审查的完整上下文与规则作出决定。

## 4. 忙碌路由秘书

助理防抖截止时，如果已经存在运行中的远程应答委托，也需要秘书选择由谁处理。

秘书获得：

- 本次防抖范围内的新消息；
- 最近有限历史；
- 当前助理工作账本；
- 当前运行中的委托 ID。

秘书只负责选择：

- 新建并发应答委托；
- 把结束锚点消息作为引导加入已有委托。

明确喊到助理时，秘书不能选择不回答。

# 五、群聊新应答委托上下文

## 1. 正式上下文范围

创建新的远程应答委托时，正式上下文从当前摘要开始，连续读取到触发消息锚点：

```text
当前摘要
→ 当前 block 中全部消息
→ trigger_message_id
```

不允许：

- 只读取防抖窗口；
- 只读取喊名群友消息；
- 跳过其他群友消息；
- 读取触发锚点之后的消息。

## 2. 冻结启动快照

应答委托创建时，会把截至触发锚点的正式上下文冻结为该委托的启动快照。

冻结的作用是：

- 保证并发委托各自拥有稳定起点；
- 避免后续新消息改变已经启动的模型请求；
- 确保同批后续消息不会提前进入较早锚点的委托。

## 3. 系统提醒

触发消息前会注入远程应答系统提醒，包含：

- 当前联系人画像；
- 当前会话正在运行的其他应答委托；
- 统一助理工作账本。

系统提醒用于避免重复应答和帮助助理理解并发工作，但不会替代正式会话上下文。

---

# 六、群聊已有应答委托的引导上下文

秘书选择 `targetDelegateId` 后，不会重新创建委托。

结束锚点消息被加入目标委托的引导队列：

```text
目标委托原冻结上下文
→ 目标委托已经消费的引导消息
→ 新的结束锚点引导消息
```

目标委托在当前模型轮次的合法检查点读取引导内容，然后继续执行。

引导不会：

- 改写其他委托的冻结上下文；
- 把当前群聊完整 block 重复复制进委托；
- 丢弃委托已经完成的工具工作；
- 强制中止正在运行的工具。

---

# 七、群聊离场反思委托上下文

联系人耐心超时且没有活跃应答委托后，群聊进入离场，并启动离场反思委托。

反思委托获得：

- 当前联系人会话已经整理好的上下文；
- 联系人负责绑定人格；
- 当前人格可见记忆；
- 统一助理工作账本；
- 本次在场期间应答委托的成功、失败和结果摘要。

反思的目标不是继续回复联系人，而是判断本次交流产生了哪些有价值记忆。

反思结果只应用：

- 有用记忆 ID；
- 记忆新增、更新、合并等操作。

反思生成的说明文本不会作为新的远程回复发送。

# 八、上下文读取对照表

| 场景 | 角色/委托 | 上下文范围 |
|---|---|---|
| 私聊空闲 | 绑定会话主助理 | 当前私聊会话连续正式上下文 |
| 私聊忙碌 | 同一个主助理 | 原上下文 + 新入库引导消息 |
| 群聊普通判断 | 秘书 | 最近有限历史 + 已入场批次的 60 秒基础巡检连续范围 + 工作账本 |
| 群聊喊名且忙碌 | 秘书 | 最近有限历史 + 助理防抖连续范围 + 工作账本 |
| 群聊新建应答 | 远程应答委托 | 当前摘要到触发锚点的完整连续上下文 |
| 群聊引导已有工作 | 已有应答委托 | 原冻结上下文 + 已消费引导 + 新锚点消息 |
| 群聊离场反思 | 反思委托 | 已整理会话上下文 + 工作账本 + 可见记忆 |

---

# 九、绝对边界

以下规则不可违反：

1. 私聊不使用秘书、群聊防抖或离场/在场上下文。
2. 群聊已入场批次中的所有新消息都追加到当前 block；未入场消息只保存，不创建巡检。
3. 未完成防抖的锚点必须存在于当前 block。
4. 正式应答上下文必须从当前摘要连续读取到触发锚点。
5. 秘书轻量判断范围不能替代助理正式上下文。
6. 防抖不能复制、拥有、过滤或移动消息。
7. 新委托不能读取触发锚点之后的消息。
8. 引导已有委托不能改写该委托的冻结启动快照。

## 一句话总结

私聊始终由当前绑定会话主助理使用连续上下文直接处理，忙碌时新消息作为引导加入；群聊则由秘书使用有限判断上下文做路由，新应答委托使用“当前摘要到触发锚点”的完整连续上下文，已有委托只追加定向引导，离场反思再结合完整会话和助理工作账本提炼记忆。
