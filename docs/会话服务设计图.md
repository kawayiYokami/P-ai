# 会话服务架构

> 更新于 2026-08-23
> 本文档描述当前会话服务（`conversation_service`）的职责边界与实现形态。早期设计中「metadata 伪装成完整会话」的风险已修复，`ConversationShardMeta -> to_metadata_conversation()` 桥接已不存在。

## 一、第一原则

会话服务的第一原则：

**除显式批准的恢复/修复流程外，任何业务调用都不得拥有破坏既有会话消息历史的能力。**

展开后包含两条硬约束：

1. 只要接口边界设计正确，任何普通调用都无法破坏会话消息。
2. 项目内禁止任何业务代码绕过 `conversation_service` 直接读写会话消息仓库。

也就是说：

- 调用方只能表达业务意图，不能表达危险实现细节
- 普通路径不能直接操作 `blocks / index / manifest / meta` 文件
- 任何跨层直读直写都视为边界失守

唯一放开的口子：

- 只有「全量导入 / 全量导出同步 / 数据迁移恢复」三类特批流程，才允许覆写整个会话
- 这是为了迁移与外部数据同步，不属于普通业务写入能力
- 除这一例外外，所有正常路径都只能追加、受限替换、受限撤销、受限压缩

## 二、三层模型

```text
+---------------------------+
| ConversationShardMeta     |
| 只含标题/状态/todo/goal  |
| 不含 messages             |
+---------------------------+
            |
            | hydrate
            v
+---------------------------+
| Conversation / Snapshot   |
| meta + full messages      |
| 只能由服务层构造          |
+---------------------------+
            |
            | persist / append / truncate
            v
+---------------------------+
| MessageStore             |
| blocks / index / manifest|
| 不直接对业务层暴露       |
+---------------------------+
```

### 1. `ConversationShardMeta`

定义在 `message_store/meta.rs`（`ConversationShardMeta`，camelCase 序列化）。

职责：

- 表达会话 metadata 的真实语义
- 可用于列表、筛选、状态判断、目标/待办读取
- 绝不能参与正文写盘

字段：`metaSchemaVersion`、`id`、`title`、`agentId`、`boundConversationId`、`parentConversationId`、`childConversationIds`、`forkMessageCursor`、`unreadCount`、`conversationKind`、`rootConversationId`、`delegateId`、`createdAt`、`updatedAt`、`lastUserAt`、`lastAssistantAt`、`status`、`userProfileSnapshot`、`shellWorkspacePath`、`shellWorkspaces`、`shellAutonomousMode`、`shellWorkMode`、`archivedAt`、`currentTodos`、`memoryRecallTable`、`planModeEnabled`、`preferredApiConfigId`、`isDraft`、`autoPushRemoteContactId`、`cumulativeUsage`、`activeGoal`、`fastRequestTurns`、`lastMessageId`、`lastMessageAt`、`messageCount`、`bodyMessageCount`、`bodyTextLength`、`hasAssistantReply`、`hasContextCompactionMessage`、`latestSummaryTitle`、`previewMessages`

服务层的展示视图是 `ConversationMetaView`（`conversation_service_v2.rs`），由 meta 派生，不携带 `messages`。

### 2. `Conversation` / 快照

- `Conversation` 是完整会话模型（含 `messages`），只能由服务层构造（`build_conversation_snapshot_from_meta` 等）
- 前端展示读取走 `get_conversation_snapshot` / 分页消息接口，不直接拼装

### 3. `MessageStore`

- 维护 `meta.json / manifest.json / messages.idx.json / blocks/*.jsonl.zstd`
- 只提供语义明确的原子能力（见 `message_store/` 模块）

## 三、服务边界

```text
UI / Scheduler / Goal / RemoteIM / Task
                |
                v
+--------------------------------------+
| ConversationServiceV2                |
|                                      |
| 读接口：                              |
| - get_conversation_meta              |
| - get_conversation_snapshot          |
| - get_messages_before / after        |
| - get_message_by_id                  |
| - get_conversation_block / last_block|
|                                      |
| 写接口：                              |
| - append_message / append_messages   |
| - append_user_message                |
| - set_title / set_todos / set_goal   |
| - rewind_conversation                |
| - archive_conversation / delete      |
| - append_tool_event_to_assistant     |
| - append_final_text_to_assistant     |
+--------------------------------------+
                |
                v
+--------------------------------------+
| MessageStore                         |
| - blocks / index / manifest / meta   |
| - 原子追加/替换/截断                  |

```

关键原则：

- UI 和调度层不能直接碰 `MessageStore` 底层函数
- `ConversationServiceV2` 不返回"伪完整会话"
- 项目内其他模块不得直接调用 message store 底层读写函数，除非属于显式恢复/修复实现

## 四、服务实现形态

入口：`conversation_service_v2()` 返回全局单例（`conversation_service_v2.rs:661`）。

模块划分（`src-tauri/src/features/chat/conversation_service/`）：

| 模块 | 职责 |
|---|---|
| `conversation_service_v2.rs` | 服务单例、错误码、核心写路径 |
| `conversation_reads.rs` | 只读接口：快照、分页、block 读取 |
| `metadata_mutations.rs` | metadata-only 更新：标题、todos、goal、pin、shell workspace |
| `history_mutations.rs` | rewind、分支、转发、删除 |
| `assistant_message_mutations.rs` | assistant 消息增量追加（工具事件/最终正文） |
| `mutations.rs` | 创建会话、停止聊天、draft 管理 |
| `archive_lifecycle.rs` | 归档、取消归档、压缩消息、导入 |
| `context_reads.rs` | 会话上下文读取与持久化 |
| `types.rs` | 服务内部结果类型 |

## 五、只读接口

| 接口 | 说明 |
|---|---|
| `get_conversation_meta(conversation_id)` | metadata 视图，不带消息 |
| `get_conversation_snapshot(conversation_id)` | 完整快照（meta + messages），需要正文时才调用 |
| `get_conversation_last_block(conversation_id)` | 尾块分页 |
| `get_conversation_block(conversation_id, block_id)` | 指定块分页 |
| `get_recent_messages_for_frontend_display_only(conversation_id, limit)` | 最近消息（前端展示投影） |
| `get_message_by_id_for_frontend_display_only(conversation_id, message_id)` | 单条消息 |
| `get_messages_before(conversation_id, anchor_id, limit)` | 锚点向前分页 |
| `get_messages_after(conversation_id, anchor_id, limit)` | 锚点向后分页 |
| `get_chat_snapshot(conversation_id)` | 会话快照（前端首屏） |
| `get_conversation_prompt_context(...)` | LLM 输入上下文准备 |

规则：

- 不需要正文的地方，只能调用 `get_conversation_meta`
- 需要正文时，必须显式调用快照或分页消息接口
- 块级读取必须显式走 block API，不能靠整会话再自行切块
- 会话列表与批量查询只能返回 meta，不能顺手带全量消息

### assistant 消息增量追加状态机

```text
OpenForToolAppend
  -> ToolHistoryGrowing
  -> FinalTextCommitted

ToolHistoryGrowing
  -> ToolHistoryGrowing
  -> FinalTextCommitted
  -> AbortedWithoutFinalText

FinalTextCommitted
  -> Closed

AbortedWithoutFinalText
  -> Closed
```

规则：

- `append_tool_event_to_assistant_message` 只允许给"尚未拥有 final 正文"的 assistant message 追加工具事件
- 一旦 assistant message 已经拥有 final 正文，后续禁止再追加任何 tool call / tool result
- `FinalTextCommitted` 之后禁止再进入 `ToolHistoryGrowing`
- `AbortedWithoutFinalText` 是合法终态（流式被压缩、中断、引导终止），不视为损坏
- 工具事件追加必须保持组级原子性，不能只落 assistant tool call 不落 tool result
- 该接口必须走 message-id 定位与尾部一致性校验，不能退化成"整条消息读出、整体替换、再写回"

### 特批覆写接口

| 接口 | 说明 |
|---|---|
| `import_conversation_snapshot` | 全量导入 |
| `sync_replace_conversation_snapshot` | 导出同步回灌 |

规则：

- 这两类接口是唯一允许整会话覆写的口子
- 必须经过 `validate_overwrite_audit` 审计
- 不得被普通聊天、工具、调度、任务、远程 IM 路径复用

## 九、分页锚点语义

- 锚点分页：`get_messages_before(anchor_id)` / `get_messages_after(anchor_id)`，锚点本身默认不包含在结果中
- 锚点必须基于全局消息顺序，不允许只在单个 block 内局部解释
- block 是物理分页单位，anchor 是逻辑分页单位，逻辑 API 不泄漏"跨 block"这类物理细节
- 分页结果返回 `messages + has_more + first/last_message_id`（`build_message_page_view_v2`）
- 工具调用消息、摘要消息、压缩上下文消息都拥有可分页的稳定 message id

## 十一、并发模型

- 单会话串行：append / replace / rewind / revoke / 归档 / 压缩 / 流式 commit / 删除必须串行化，保证 meta/manifest/index/blocks 观察到同一版本
- 多会话并发：不同会话独立锁，不共享可变消息快照；跨会话批量查询只读 meta
- 调度层与消息存储通过 `ConversationServiceV2` 交互，调度器不直接碰 store 底层

## 十二、一致性规则

每次提交后必须同时满足：

1. `meta.message_count == manifest.source_message_count == index.items.len()`
2. `meta.last_message_at` 与 index 最后一条消息一致
3. `preview_messages` 与真实消息尾部投影一致
4. `body_message_count / body_text_length` 与当前正文一致

存储层提交采用"写临时文件 -> 原子替换 -> cleanup 尾动作"顺序，stale block cleanup 必须是提交成功后的尾动作，不能先删后写。
